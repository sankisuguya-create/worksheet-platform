# 検証スクリプト

`scripts/check-palette.mjs`。Node 18以降。依存ライブラリなし。

## 使い方

```bash
# 線・アイコン・小面積（既定 role=mark、各色 vs 背景 3.0 以上を要求）
node scripts/check-palette.mjs "#0F5EA8,#C86A00,#6E4310"

# 塗り（role=tint、載せる文字との比 4.5 以上、白地から浮くこと 1.15 以上）
node scripts/check-palette.mjs --role tint --on "#1A1A1A" "#D7E8F8,#FBE3B4"

# 文字色としても使う色を追加検査（vs 背景 4.5 以上）
node scripts/check-palette.mjs --text "#0F5EA8,#C0330A" "#0F5EA8,#C0330A"

# 暗背景
node scripts/check-palette.mjs --bg "#1A1A1A" "#6FA8DC,#E8A33D"

# 既定パレット
node scripts/check-palette.mjs --preset mark4
node scripts/check-palette.mjs --role tint --preset tint2

# CI・自動処理向け
node scripts/check-palette.mjs --json "#0F5EA8,#C86A00"   # 不合格があれば終了コード1
```

## 出力の読み方

| 記号 | 意味 | 扱い |
|---|---|---|
| ◎ | 色相でも明度でも分離 | そのまま使える |
| ○（明度差のみ） | 色が潰れる型があるが明度で残る | **形・位置・ラベルの併用が必須** |
| ✗ | どの型かで同色になる | 使えない。色を差し替える |

`1型で潰れる` などの表示は、その色覚タイプのシミュレーション下でΔE00が閾値を下回ったことを指す。

## 何を計算しているか

1. **色覚シミュレーション** … Viénot, Brettel & Mollon (1999) の2色覚モデル。sRGB→線形RGB→LMS→欠損軸の投影→sRGB。1型(P)・2型(D)・3型(T)の**強度**（dichromacy）で計算する。弱度（anomalous trichromacy）は強度より見分けやすいので、強度で通れば弱度でも通る。安全側に倒してある。
2. **色差** … CIEDE2000。sRGB→XYZ(D65)→CIELAB。
3. **明度差** … WCAG 2.x の相対輝度比。色相が潰れても残る唯一の手がかりなので、色差の代替として評価する。
4. **背景コントラスト** … 役割別。mark は WCAG 1.4.11（非文字 3:1）、text は WCAG 1.4.3（本文 4.5:1）。

## 閾値と、その根拠

```js
{ dE: 18, lumRatio: 1.25, markBg: 3.0, tintOn: 4.5, tintBg: 1.15, textBg: 4.5 }
```

- `markBg` `tintOn` `textBg` は **WCAG 由来**（規格値）。
- `dE: 18` と `lumRatio: 1.25` は **本スキル独自の較正値であり、規格ではない**。CIEDE2000 の ΔE=1 が識別限界、2〜3で気づく差だが、UIでのカテゴリ識別は小面積・離れた位置・記憶を挟むため、それよりはるかに大きい差を要る。18は下の較正で決めた。15未満に下げると、シミュレーション画像で明らかに同色に見えるペアが通ってしまう。
- `lumRatio: 1.25` は「隣接する面の明暗の違いに気づく」水準として置いた。読みやすさの要件ではないので WCAG の 3:1 より緩く、代わりに**形の併用を必須**にすることで担保している。

## 較正記録

**既知のCUD配色（Okabe & Ito 7色）を通した結果**（`--preset cud`）

- 7色すべてを同時に使うと、`#009E73`（緑）×`#CC79A7`（赤紫）が2型で ΔE00 18.0 まで落ち不合格。`#E69F00`×`#F0E442` は2型11.7、3型8.6。→ **CUD推奨色であっても、7色を一度に使えば区別できない組み合わせが生じる**。色数の上限が色の選択より先に効く、という本スキルの構成はここから来ている。
- 白地でのコントラストは `#F0E442`（黄）が1.3、`#E69F00` と `#56B4E9` が2.3。→ CUD配色は**線とマーカー用**であり、白地の面や文字にそのまま使うと沈む。役割（mark / tint / text）を分けて検査する設計はここから来ている。

**淡色3色の実測**（`--role tint`）

| 組 | 最悪ΔE00 |
|---|---|
| 青淡 × 黄淡 × 灰 | 6.7（1型、青淡×灰） |
| 青淡 × 黄淡 × 緑淡 | 6.5（3型） |
| 青淡 × 黄淡 × 紫淡 | 1.9（1型、青淡×紫淡） |

→ **淡色で3カテゴリを区別することは、色の選び方を変えても成立しない。** 塗りは2色までという上限はこの実測による。

**濃い文字色4色の実測**

`#0F5EA8, #A85800, #6E4310, #616870` … 青×灰 ΔE00 17.0（一般色覚で既に不合格）、橙×茶 10.8（1型）。→ **文字の明度域では色相の差が縮む。文字色で4カテゴリは不可能。** 文字色2色という上限はこれによる。

## 限界

- シミュレーションは**強度2色覚**のモデル。錐体の分光感度がずれる弱度（1型3色覚など）は再現していない。強度で通せば弱度も通るという前提で安全側に運用する。
- 白内障・加齢による水晶体の黄変は**計算していない**。黄変は青系の識別を落とすため、青系どうしの濃淡（`--cat-1` と淡い青）だけで意味を分ける設計は、スクリプトが通っても避ける。
- ディスプレイのキャリブレーション、視野角、周囲光は考慮していない。児童機の液晶は視野角が浅く、実測より条件は悪い。**閾値ぎりぎりで通った配色は、通らなかったものとして扱う。**
